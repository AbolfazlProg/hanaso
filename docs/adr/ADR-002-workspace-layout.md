# ADR-002 — Lightweight Workspace Layout (apps/ + packages/)

**TL;DR (فارسی):** این ریپو پوستهٔ Monorepo سبک pnpm (`apps/web` + `packages/*`) دارد اما همچنان **یک اپ قابل-استقرار** است — تطبیق Controlled Deviation با ADR-001 KB که «تک-اپ بدون monorepo» می‌گفت؛ دلیل: الزام ساختاری مأموریت مالک (§۱۳) + مرزهای مالکیت چند-Agentی.

- **مسئله:** ADR-001 KB ساختار «تک-اپ در ریپوی واحد (بدون monorepo)» را پین کرده بود؛ مأموریت مالک §۱۳ حداقل‌های `apps/`, `packages/`, `docs/`, `tests/`, `infra/`, `scripts/`, `agent-skills/`, `.github/` را خواست؛ تناقض ظاهری باید حل می‌شد.
- **گزینه‌ها:** (۱) تک-اپ مسطح طبق KB · (۲) پوستهٔ workspace سبک با یک اپ deployable · (۳) monorepo کامل چند-اپ (web/admin/docs جدا).
- **شواهد:** مأموریت §۱۳ «ساختار نمونه است؛ بی‌دلیل پیچیده نکن»؛ §۵.۳ مالکیت فایل‌ها بر اساس ماژول؛ اصل ADR-001 KB «تک-استقرار» در گزینهٔ ۲ هم کاملاً حفظ می‌شود (یک Dockerfile/یک image/یک pipeline)؛ admin از ADR-017 داخل همان مونولیت است نه اپ جدا.
- **مقایسه:** گزینهٔ ۱ الزام مأموریت را نقض می‌کرد؛ گزینهٔ ۳ با «بدون میکروسرویس/بدون اپ جدا» ADR-001/017 در تعارض و پیچیدگی بی‌دلیل. گزینهٔ ۲ هر دو را جمع می‌کند.
- **تصمیم:** pnpm workspace با `apps/web` (تنها اپ قابل-استقرار، standalone) + `packages/*` (فقط وقتی قرارداد مشترک واقعی شکل گرفت — فعلاً placeholder مستند) + بقیهٔ پوشه‌های مأموریت. ماژول‌های دامنه‌ای مثل KB داخل `apps/web/src/modules/*`.
- **مزایا:** مرزهای مالکیت واضح Agentها · آمادهٔ پکیج‌های قراردادی آینده (content-schema/events-types) · تک-استقرار حفظ شد. **معایب:** یک لایهٔ غیرمستقیم اضافه (پذیرفته).
- **هزینهٔ تغییر آینده:** بازگشت به تک-اپ مسطح = جابه‌جایی پوشه‌ها + به‌روزرسانی configها (کم)؛ شکستتن به چند-اپ = مهاجرت معماری واقعی (زیاد — نیازمند ADR جدید).
- **ریسک‌ها:** ابزارها باید workspace را درست بفهمند (مسیر standalone تودرتو با اجرای واقعی سرور محلی اعتبارسنجی شد؛ build کامل Image نیازمند نخستین محیط Docker در M0-10)؛ ثبت انحراف از ADR-001 KB از مسیر spec-gap انجام شد تا drift مدارکی نداشته باشیم.
- **وضعیت تأیید:** `PROPOSED` — پیشنهاد به‌روزرسانی ADR-001 KB ثبت شد (spec-gap issue).
