## ۲. خلاصهٔ سادهٔ پروژه

**هاناسو (HANASO) چیست؟** وب‌سایت آموزش زبان ژاپنی برای فارسی‌زبانان؛ مکالمه‌محور، با سه شخصیت انیمه‌ای همراه، تکرارهای هوشمند (FSRS) و مسیر یادگیری مبتنی بر «جزیره‌های یادگیری». دامنهٔ نهایی: `hanaso.ir`.

**تاکنون چه ساخته شده؟** زیرساخت مهندسی کامل (مخزن کد، تست‌های خودکار، خط تولید نسخه)، یک نمونهٔ فنی کامل از چرخهٔ یادگیری (گفت‌وگو ← درس ← تمرین ← آزمون)، زیرساخت رابط کاربری دوزبانه (فارسی راست‌به‌چپ + ژاپنی با تلفظ‌نویسی روبی)، و **نخستین استقرار زنده** روی آدرس آزمایشی learn.kotodama.ir.

**الان روی چه چیزی کار می‌کنیم؟** وصل‌کردن Database واقعی به سرور زنده (Postgres + بکاپ)، سپس اولین درس نمایشی و سیستم حساب کاربری. چرا اولویت دارد؟ چون تا Database وصل نشود، هیچ دادهٔ کاربر (پیشرفت، مرورها، حساب) ماندگار نمی‌شود و قابلیت‌های بعدی همه به آن وابسته‌اند.

**چه بخش‌هایی آماده نیستند؟** روش تدریس نهایی (در انتظار نتیجهٔ تحقیق آموزشی)، طراحی هنری سه شخصیت (در انتظار Agent هنری و تأیید مالک)، مسیر بصری نهایی (دو گزینهٔ هنری آمادهٔ انتخاب مالک است)، سیستم پرداخت، و ایمیل/پیامک.

## ۶. سه کار بعدی (رتبه‌بندی با دلیل)

### ۱) اتصال Database واقعی به سرور زنده (ادامهٔ M0-10) — _Builder، بدون نیاز به تصمیم مالک_

- **چه می‌شود؟** نصب Postgres + PgBouncer روی همان سرور + اتصال اپ + اولین بکاپ اثبات‌شده.
- **چرا لازم است؟** بدون Database، پیشرفت کاربر و حساب‌ها ماندگار نمی‌شوند؛ تقریباً همهٔ قابلیت‌های بعدی به آن وابسته‌اند. سرور آماده است و ظرفیت کافی دارد.
- **بعد از آن چه ممکن می‌شود؟** سیستم حساب کاربری (M1)، ذخیرهٔ واقعی پیشرفت، درس نمایشی ماندگار.
- **نیاز به تصمیم مالک؟** خیر (زیرساخت فنی؛ تصمیم‌های ذخیره‌سازی قبلاً در KB ثبت شده‌اند).

### ۲) راه‌اندازی Agent هنری شخصیت‌ها (TASK-CHR-01..05) — _مالک_

- **چه می‌شود؟** Agent مستقل طراحی، سه شخصیت را طبق «کتاب شخصیت» می‌سازد.
- **چرا لازم است؟** طولانی‌ترین مسیر تولید محسوس محصول است؛ قرارداد فنی (ADR-018) و ۱۲ Issue آماده‌اند تا خروجی بدون بازنویسی کد وصل شود.
- **بعد از آن چه ممکن می‌شود؟** جایگزینی جایگزین‌های فعلی با شخصیت‌های واقعی + انیمیشن سر و صورت + صداگذاری هر شخصیت.
- **نیاز به تصمیم مالک؟** **بله** — راه‌اندازی Agent و سپس تأیید نهایی طرح‌ها (#50).

### ۳) تسویه بدهی‌های فنی ثبت‌شده (#66..69 و #72) — _Builder_

- **چه می‌شود؟** موارد کوچک باقی‌مانده از بازبینی‌ها (به‌هم‌پیوندی تکرار هوشمند، ارقام فارسی، …).
- **چرا لازم است؟** کیفیت مسیر یادگیری واقعی را قبل از ساخت M1 تضمین می‌کند؛ ریسک انباشت بدهی را حذف می‌کند.
- **بعد از آن چه ممکن می‌شود؟** شروع تمیز M1 (حساب کاربری).
- **نیاز به تصمیم مالک؟** خیر.

| `/poc/ui`                                   | صفحهٔ مرجع مهندسی رندر دوزبانه — ابزار آزمون کیفیت، نه صفحهٔ محصول.                                                                                                     |
| ظاهر فعلی سایت                              | مبتنی بر توکن‌های پایهٔ مصوب است اما **ظاهر نهایی نیست** (دو گزینهٔ هنری منتظر انتخاب‌اند)؛ تغییر ظاهر بعدی فقط با تعویض توکن‌ها انجام می‌شود، بدون بازنویسی.           |

## ۹. واژه‌نامهٔ ساده

| اصطلاح                       | یعنی چه؟                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------ |
| **Commit**                   | یک «عکس فوری» از تغییرات کد در یک لحظه؛ با شناسهٔ یکتا (مثل `42a6bc3`) قابل ارجاع است.     |
| **Branch (شاخه)**            | کپی موازی از کد برای کار روی یک قابلیت بدون خراب‌کردن نسخهٔ اصلی.                          |
| **Pull Request (PR)**        | درخواست «بررسی و ادغام» تغییرات یک شاخه در شاخهٔ اصلی؛ همراه با توضیح، آزمون‌ها و بازبینی. |
| **Merge**                    | پذیرش و ادغام PR در شاخهٔ اصلی (main).                                                     |
| **CI**                       | ربات تست خودکار GitHub که با هر تغییر، کل کیفیت را می‌سنجد (سبز = سالم).                   |
| **Deployment (استقرار)**     | منتشرکردن کد روی سرور واقعی تا از اینترنت دیده شود.                                        |
| **Preview**                  | نسخهٔ آزمایشی زنده برای مرور — اینجا: learn.kotodama.ir (نه سایت نهایی hanaso.ir).         |
| **API**                      | مسیرهای پشت صحنهٔ سایت که داده رد و بدل می‌کنند (مثل /api/health).                         |
| **Database Migration**       | تغییر ساختار جدول‌های پایگاه داده به‌صورت نسخه‌دار و قابل بازگشت.                          |
| **Feature**                  | یک قابلیت محصول (مثلاً «مرور روزانه»).                                                     |
| **Milestone**                | مجموعه‌ای از کارها با هدف مشترک (مثلاً M1 = تجربهٔ یادگیری اول).                           |
| **Acceptance Criteria (AC)** | معیارهای پذیرش: شرط‌هایی که اگر برقرار نباشند، کار «انجام‌شده» حساب نمی‌شود.               |
| **Prototype / نمونهٔ فنی**   | نسخه‌ای برای اثبات امکان‌فنی؛ لزوماً نهایی یا مصوب نیست.                                   |
| **Production**               | محیط واقعی محصول نهایی در دست کاربران (هنوز راه‌اندازی نشده — M7).                         |
| **Blocker**                  | مانعی که کار را متوقف می‌کند تا کسی آن را حل کند (اینجا معمولاً = تصمیم مالک).             |
| **FSRS**                     | الگوریتم زمان‌بندی مرور هوشمند (نسخهٔ قوی‌تر سیستم فلش‌کارت).                              |
| **روبی (Ruby/Furigana)**     | تلفظ‌نویسی کوچکی که بالای کلمات ژاپنی می‌نشیند.                                            |
| **KB (مرکز دانش)**           | مخزن مستقل پژوهش/طراحی/تصمیم‌ها؛ مرجع نهایی حقیقت پروژه.                                   |
