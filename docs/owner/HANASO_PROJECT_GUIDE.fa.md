## فصل ۱ — HANASO چیست؟

**هاناسو (HANASO)** وب‌سایت آموزش زبان ژاپنی برای فارسی‌زبانان است؛ «هاناسو» یعنی «حرف زدن» — چون محصول **مکالمه‌محور** است.

- **کاربران:** فارسی‌زبانانی که ژاپنی یاد می‌گیرند — از مبتدی (N5) تا سطح متوسط. رابط فارسی/راست‌به‌چپ، محتوای ژاپنی با تلفظ‌نویسی (روبی/فوریگانا) و ترجمهٔ فارسی.
- **ارزش اصلی:** به‌جای فلش‌کارت‌های خشک، یادگیری از دل **مکالمه‌های واقعی** با سه شخصیت انیمه‌ای همراه (میکی، یامادا، سورا — در حال طراحی)، تکرارهای هوشمند (الگوریتم FSRS) و مسیر یادگیری بر پایهٔ «جزیره‌های یادگیری» (هر جزیره = یک دنیای کوچک مثل کافه/ایستگاه).
- **چرخهٔ یادگیری (A→D):** هر واحد آموزشی ۴ مرحله دارد: **A** خودآزمایی با مکالمه ← **B** درس از دل همان مکالمه ← **C** تمرین ← **D** ارزیابی فهم. فقط وقتی کاربر در D ثابت کند «فهمید» (understood) — نه صرفاً «تمام کرد» — واحد بسته می‌شود. این تفاوت عمدی با اپ‌های رایج است.
- **دامنهٔ نهایی:** `hanaso.ir` (فعلاً سایت آزمایشی روی `learn.kotodama.ir` است).

## فصل ۵ — طراحی و Aizen

- **جهت هنری:** **Aizen (藍染)** — انتخاب قطعی مالک (تصمیم DD-084 در مرکز دانش). هویت: کاغذ گرم + جوهر مشکی + شنگرف (قرمز) + نیلی؛ قاب‌های newspaper؛ موتیف موج 青海波؛ مُهر دایره‌ای «فهمیدم»؛ سادگی ژاپنی.
- **Design Tokens:** همه در `apps/web/src/styles/tokens.css` — رنگ/فاصله/سایه/شعاع گوشه/تایپ از یک منبع واحد؛ کامپوننت‌ها hex خام ندارند (دروازهٔ tokens-gate این را تست می‌کند).
- **فونت‌ها:** فارسی + ژاپنی سلف‌هاست (بدون CDN خارجی — مناسب ایران) با بودجهٔ ۱.۷۳MB و دروازهٔ چک.
- **وضعیت صفحات:** جدول فصل ۴ + نمرات ممیزی بصری (۴ تا ۷.۵ از ۱۰ — بهترین: ویترین `/poc/ui`).
- **شکاف‌های طراحی (ثبت‌شده در ممیزی):** اعمال ناهمگن امضاها در صفحات؛ نبود حالت‌های انتخاب در تمرین/ارزیابی؛ فوترهای متنی/فنی؛ هم‌ترازی فونت سه‌زبانه؛ نبود هرگونه دارایی تصویری (0 تصویر — منتظر شخصیت‌ها).
- **قاعدهٔ ادامه:** طراحی از صفر بازنویسی **نمی‌شود**؛ پالایش از طریق همان توکن‌ها انجام می‌شود.

## فصل ۶ — معماری فنی (به زبان ساده + نقشه)

**ساختار کد:** یک مخزن، یک اپ قابل‌استقرار (`apps/web` — Next.js 16) + ابزارها. «مونولیت ماژولار» یعنی همه در یک بسته ولی ماژول‌های مرزبندی‌شده (dialogue/mastery/practice/progress/fsrs/audio/character).

**اجزای زنده:**

1. **فرانت‌اند** (۸ صفحهٔ فعلی) → 2. **API** (۶ مسیر با اعتبارسنجی zod و پوشش خطای یکنواخت) → 3. **دیتابیس PostgreSQL 18.6** از طریق **PgBouncer** (مدیر اتصال) → 4. **Worker** (پس‌زمینه: بکاپ شبانه + صحت‌سنجی روزانه) → 5. **استقرار** (داکر روی سرور مشترک؛ پشت HAProxy/nginx میزبان؛ TLS).

**چیزی که هنوز نیست:** حساب کاربری (بهتر-auth در M1) · پنل مدیریت (M6) · ذخیرهٔ تحلیلی (M6) · خط تولید صوت واقعی (M3a) · ذخیره‌سازی فایل خارج از دیتابیس.

## فصل ۷ — ساختار آموزش (مفاهیم + مثال واقعی)

سلسله‌مراتب: **Level** (سطح، مثل N5) ← **Chapter/جزیره** (دنیای موضوعی) ← **Dialogue** (مکالمهٔ لنگر) ← **Lesson** (درس از دل مکالمه) ← **تمرین‌ها** ← **ارزیابی (Mastery)**.

**مثال واقعی موجود در دیتابیس امروز:** مکالمهٔ «کافه‌ای در توکیو، صبح» (`cafe-morning-01`) با ۳ شخصیت (یامادا: صاحب کافه · میکی: مهمان اصلی · سورا: همراه) و ۱۰ خط گفتار — کاربر می‌رود: A می‌شنود/می‌خواند → B درس → C شش نوع تمرین → D ارزیابی سروری؛ اگر قبول شود، وضعیت واحد `understood` می‌شود و در `/learn` دیده می‌شود. (همین الان با کاربر آزمایشی `poc-user` واقعاً کار می‌کند.)

**Station/Terminal (ایستگاه‌ها):** از TASK-LEARNING-01 در محصول پیاده شد — فصل ۱ («اولین دیدار») ۱۰ ایستگاه اصلی + ۲ اختیاری دارد که ترتیبشان فقط از داده می‌آید؛ نقشهٔ جزیره‌ای در `/learn/first-meeting-01/journey` قابل مرور است. (اسناد کامل: `docs/engineering/learning/`)

| اصطلاح                | یعنی                                                                             |

| **Commit**            | عکس فوری از تغییرات کد با شناسهٔ یکتا (مثل `eb80e88`)                            |

| **Milestone**         | مجموعه‌کار با هدف مشترک (M1 = تجربهٔ یادگیری اول)                                |
| **CI**                | ربات تست خودکار GitHub — «سبز» یعنی همه سالم                                     |

### چطور بدانیم Agent واقعاً کار کرده، نه فقط گزارش داده؟

1. **PR را باز کنید** — تغییرات فایل واقعی را ببینید (تب Files changed)؛ گزارش بدون PR = هوا.
2. **CI سبز** روی همان PR (تب Checks) — تست‌ها خودکار اجرا شده‌اند.
3. **رکورد اجرا** در `ops/runs/RUN-*.md` با بخش شواهد (خروجی واقعی دستورها).
4. **جدول «Skills used»** در PR — پس از PR #76 اجباری است؛ خالی = نقص فرایند.
5. برای کارهای استقراری: آدرس سایت و `/api/health` (فیلد commit باید با merge منطبق باشد).
6. برای ادعاهای تست: عدد تست باید در CI قابل بازتولید باشد (مثلاً «۱۵۱ واحد + ۳۲ integration»).

### قالب واگذاری کار (کپی کنید و پر کنید)

```
هدف کار:
دلیل (چه مشکلی حل می‌شود / چه ارزشی می‌سازد):
خروجی مورد انتظار (چه چیزی را باید ببینم):
محدودهٔ تغییر (کدام بخش‌ها مجازند):
موارد خارج از Scope (صریحاً ممنوع):
محدودیت‌ها (فنی/زمانی/بودجه):
کیفیت مورد انتظار (تست/بازبینی/دروازه‌ها):
تست و پذیرش (چطور بفهمیم درست است):
وضعیت Deployment (deploy لازم است یا نه):
```

### قواعد جاری

- Agentها فقط از طریق PR به main می‌رسند؛ هر PR باید CI سبز + بازبینی مستقل داشته باشد.
- فایل‌های مشترک (مثل `PROJECT_STATUS.md`) ترتیبی تغییر می‌کنند — Agent در `AGENT_PROGRESS.md` اعلام هم‌نقطه می‌کند.
- پیش از هر تسک، Agent باید Skillهای همان نوع کار را از ماتریس انتخاب بخواند (۲–۴ مورد) و در پایان اعلام کند.
- **Merge چه زمانی؟** CI سبز + بازبینی مستقل + عدم تداخل با کار موازی.
- **Deploy چه زمانی؟** فقط وقتی کد _محصول_ تغییر کرده (مستندات deploy نمی‌خواهند).
- **موازی‌کاری:** مجاز با فایل‌های ناهم‌نقطه — مالک فقط باید مطمئن شود دو Agent روی یک فایل نیستند (دفتر `AGENT_PROGRESS.md`).

### سه دام اصلی (از تجربهٔ همین پروژه)

1. **شمارهٔ رکورد اجرا تکراری** (دو سشن موازی هر دو RUN-…-02 ساختند) — در PR #76 حل شد؛ اگر دیدید دو رکورد هم‌شعاره، یکی باید بازشماره شود.
2. **ادعای نیمه‌کارهٔ سشن قبلی** (M0-10 «۸۵٪» گزارش شده بود ولی روی دیسک چیزی نبود) — همیشه شاهد فایل/شاخه بگیرید.
3. **استقرار با کد مستنداتی** — لازم نیست؛ فقط تغییر کد محصول deploy می‌خواهد.
