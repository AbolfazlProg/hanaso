## ۱. روش

صفحهٔ client موقت (`src/app/spike-ruby-rtl/`) با ۸ سناریو + بخش اندازه‌گیری خودکار: هر سناریو در پاراگراف RTL (`direction: rtl`, فونت Vazirmatn 17px, line-height 1.9 — و 1.4/2.0 برای سناریوی ۵). بعد از `document.fonts.ready` صفحه خودش هندسهٔ `ruby/rt/متن فارسی` را با `getBoundingClientRect` و `Range.getClientRects()` می‌سنجد؛ اعداد همین‌هاست. صحت بصری ۳ یافتهٔ کلیدی با مدل بینایی (GLM-5V) روی اسکرین‌شات‌ها راستی‌آزمایی شد.

## ۲. یافتهٔ حیاتی — بدون جزیرهٔ LTR، جملهٔ روبی‌دار **وارونه** رندر می‌شود

مهم‌ترین نتیجهٔ این اسپایک (و جواب واقعی FT-003):

- متن ژاپنیِ **خالص و پیوسته** داخل پاراگراف RTL درست رندر می‌شود (آزمون مستقیم: 今 در x=1225 < す در x=1327 — یک L-run واحد).
- اما به‌محض اینکه جملهٔ ژاپنی با **عناصر inline** (اول همه: `<ruby>`) قطعه‌قطعه شود، Chromium قطعات را در جهت پاراگراف (RTL) می‌چیند: **ترتیب واژه‌های جمله برعکس می‌شود**. در s6b جملهٔ `行(おこな)う、食(た)べる、見(み)る` از چپ به راست این‌طور دیده شد: `る。 う、 食た べる、 見み 行おこな` — یعنی سطر از نظر خوانندهٔ ژاپنی کاملاً خراب است. همین خرابی در s2a، s4 و s7 (بدون dir) اندازه‌گیری و با VLM روی اسکرین‌شات s2a تأیید شد («ترتیب واژه‌ها کاملاً وارونه است»).
- **راه‌حل (هر سه راه آزموده و سالم):** دور کل قطعهٔ ژاپنی: `span dir="ltr" lang="ja"` یا `<bdi>` یا CSS `direction: ltr; unicode-bidi: isolate` — ترتیب قطعات در هر سه صحیح ماند (اندازه‌گیری مستقیم ترتیب x).
- نتیجه برای ما: قانون طلایی شمارهٔ ۱ KB (`bilingual-rtl-ltr` §۱) **از جنس «بهتر است» نیست، شرط صحت است»** — بدون آن خروجی قابل‌خواندن نیست. `FuriganaText` این ایزوله‌سازی را باید خودش اعمال کند (§۶).

## ۳. جدول سناریوها (اعداد واقعی دسکتاپ؛ rt = furigana)

| سناریو | نتیجه | عدد کلیدی |
|---|---|---|
| ۱) تک‌روبی وسط جملهٔ فارسی | ✅ سالم | rt دقیقاً بالای پایه و **وسط‌چینِ بی‌نقص** (انحراف مرکز = 0.0px)؛ کف جعبهٔ ruby با کف جعبهٔ متن فارسی یکی (`bottomDelta=0`) — یعنی کانجی و متن فارسی روی یک خط پایه می‌نشینند |
| ۲a) چندروبی + علائم JP (بدون dir) | ❌ ترتیب وارونه | ببین §۲؛ فاصله‌گذاری داخلی هر روبی سالم |
| ۳a) همان داخل `bdi` | ✅ | ترتیب صحیح؛ هندسهٔ rt مثل s1 |
| ۳b) همان داخل `span dir="ltr" lang="ja"` | ✅ | الگوی KB — ترتیب صحیح |
| ۴) کاتاکانا/کانجی ترکیبی (بدون dir) | ❌ ترتیب وارونه | مثل s2a |
| ۵a) line-height 1.4 + شکست خط | ❌ برخورد بصری | جعبهٔ rt **6px داخل جعبهٔ متن سطر فارسیِ قبل** نفوذ می‌کند (۵ روبی از ۵)؛ half-leading فارسی در 1.4 منفی است (−1.1px) ⇒ برخورد واقعی جوهر قلم — VLM تأیید کرد |
| ۵b) line-height 2.0 (همان محتوا) | ✅ | نفوذ جعبه‌ای فقط 3px که در half-leading مثبت (+4px) جذب می‌شود — VLM: «هیچ هم‌پوشانی دیده نمی‌شود» |
| ۶a) rt بلند روی پایهٔ ۳حرفی (東京都→とうきょうと) | ✅ | پایه با `space-around` به عرض rt کشیده می‌شود؛ بدون overhang |
| ۶b) rt بلند روی پایهٔ ۱حرفی (行→おこな) | ⚠️ | عرض rt=36px == عرض متن پایه=36px ⇒ حرف پایه‌ تک‌حرفی دور از حرف بعدی «باز» می‌شود (توزیع space-around؛ VLM تأیید). بدون هم‌پوشانی با همسایه، ولی چهرهٔ متن کمی کشیده — برای مبتدی قابل‌قبول |
| ۷) `ruby-position: under` | ✅ (گزینهٔ جایگزین) | rt می‌رود زیر پایه (rtTopDelta=−20)؛ ترتیب bidi مثل over است (همچنان نیازمند island) |
| ۸) الگوی پیشنهادی island + Zen Kaku + rt توکن‌دار | ✅ | همهٔ سناریوها سبز: ترتیب صحیح، rt بالا/وسط، ایزوله (`direction:ltr`, `unicode-bidi:isolate`) — نسخهٔ Serif (Noto Serif JP) هم سالم |

**پیش‌فرض‌های محاسبه‌شدهٔ Chromium 156:** `ruby-position: over` · `ruby-align: space-around` · rt همیشه بالای پایه در `writing-mode: horizontal-tb` — جهت RTL تأثیری بر جای rt ندارد (برخلاف عمودی که over=راست است).

## ۴. line-height — اعداد تصمیم‌گیر

آزمون A/B ایزوله (رفتار واقعی Chromium برای رزرو فضا):

| line-height | رشد سطرِ دارای روبی |
|---|---|
| 1.4 | +13px (تک‌خط: 23.8 → 36.8px) |
| 1.9 | +8px |
| 2.0 | +7px |

یعنی Chromium فضای rt را «تا حدی» رزرو می‌کند؛ ولی جعبهٔ متن Vazirmatn در 17px خودش 26px است — بلندتر از سطرِ 1.4 (23.8px). نتیجهٔ خالص همان §۳-۵a است:

- **قاعدهٔ KB «سطر روبی‌دار line-height ≥ 2» با عدد تأیید شد** (نفوذ 3px < half-leading 4px ⇒ امن؛ در 1.9 مرزی و در 1.4 ناامن).
- توصیهٔ اجرایی: پاراگراف‌های حاوی `FuriganaText` در tokens با `--leading-ja: 1.9`ِ عادی رها نشوند؛ یا `line-height: 2` روی کلاس `.fg-block` یا «فاصلهٔ مثبت حداقل (2−1.9)×17px ≈ 2px اضافی» تأمین شود. ساده‌ترین قاعدهٔ قابل-lint: **هر p/blockی که ruby دارد → `line-height >= 2`**.

## ۵. انتخاب متن، rp، عرض rt

- **کپی/انتخاب:** furigana به‌طور پیش‌فرض داخل متنِ کپی می‌آید (`今日きょうは…`). تست زنده: `rt { user-select: none }` کپی را کاملاً تمیز کرد (`今日は良天気です。…`) ⇒ این قاعده در CSS پایهٔ ما باشد (کاربر که معنی می‌خواهد پاپ‌آور M0-06/tooltip دارد؛ کپی باید جملهٔ تمیز بدهد).
- **rp:** در Chromium `display:none` ✓ — پس `<rp>(</rp>` را برای مرورگرهای پشتیبان بدون ریسک اضافه می‌کنیم (اندازه‌گیری شد).
- **rt پهن‌تر از پایه:** رفتار Chromium = کشیدن/پخش پایه (space-around)، نه overhang روی متن مجاور؛ همسایه‌ها هرگز زیر روبی نمی‌روند (VLM تأیید). برای روبی‌های بسیار بلند (۱ کانجی + ۴+ کانا) به‌جای فشرده‌سازی، اجازهٔ پهن‌شدن بدهیم.

## ۶. الگوی رندر توصیه‌شده `FuriganaText` (ورودی مستقیم M0-09)

### ۶-۱. قرارداد props

```ts
// apps/web/src/modules/ui/types.ts (طرح — در این اسپایک پیاده نشد)
export type FuriganaToken =
  | { t: 'plain'; v: string }                     // متن بدون روبی: は
  | { t: 'ruby'; base: string; rt: string };      // group-ruby: 今日/きょう

export interface FuriganaTextProps {
  tokens: FuriganaToken[];        // یا children با DSL رشته‌ای: «今日|きょう|は…»
  lang?: string;                  // پیش‌فرض 'ja' (WCAG 3.1.2)
  variant?: 'ui' | 'serif';       // فونت: Zen Kaku Gothic New | Noto Serif JP
  position?: 'over' | 'under';    // پیش‌فرض 'over' (سازگار با KB)
}
```

- هر «قطعهٔ ژاپنی» = یک فراخوانی `FuriganaText` = یک island. مرزهای پاراگراف فارسی، همان مرز token هاست.
- **group-ruby فقط** (per KB: jukugo در Blink خراب است): هر پایه یک واحد معنایی/خوانشی، هرگز توزیع کاراکتری.

### ۶-۲. CSS پیشنهادی (با اعداد همین اسپایک)

```css
.fg {                                        /* ریشهٔ FuriganaText */
  direction: ltr;                            /* §۲ — شرط صحت، نه سلیقه */
  unicode-bidi: isolate;
  font-family: var(--font-ja-ui);            /* variant=serif → var(--font-ja-serif) */
}
.fg ruby { ruby-position: over; ruby-align: center; }
.fg rt {
  font-size: max(0.5em, 12px);               /* توکن --furigana-size (KB) */
  font-weight: 400;
  letter-spacing: 0;
  line-height: 1;                            /* جعبهٔ 17px→~12px؛ نفوذ به سطر قبل کمتر */
  user-select: none;                         /* §۵ — کپی تمیز */
}
.fg-block, :has(> .fg) { line-height: 2; }   /* §۴ — قاعدهٔ ≥2 برای بلوک روبی‌دار */
```

- `ruby-align: center` (پشتیبانی Chrome 128+) و `space-around` (پیش‌فرض) در سناریوهای ما خروجی یکسان داشتند؛ center برای group-ruby هدف‌گیری JVREQ-تر است. اگر مرورگر پشتیبانی نداشت، پیش‌فرض مرورگر هم سالم بود (s1 بدون ruby-align دقیقاً وسط‌چین شد).
- خط پایه به‌طور خودکار با متن فارسی هم‌تراز می‌شود (`bottomDelta=0` — نیازی به تنظیم دستی نیست).

### ۶-۳. قواعد bidi isolation (چک‌لیست پیاده‌سازی)

1. ریشهٔ هر `FuriganaText`: `direction: ltr` + `unicode-bidi: isolate` (+ `lang="ja"`).
2. **هرگز** دو island ژاپنی را با متن فارسی بین آن‌ها در یک گره inline نچینیم بدون اینکه هر کدام isolate باشند — چیدمان s2a ثابت کرد ترتیب بدون isolate وارونه می‌شود.
3. متن کاربر جهت-نامعلوم (نام‌ها، یادداشت): `bdi` یا `unicode-bidi: plaintext`.
4. «متن سادهٔ ژاپنی» (بدون روبی) هم از همان island استفاده کند — یک مسیر رندر، یک قاعده (و رفتار متن خالص هم با island فقط بهتر می‌شود).
5. خروجی متنی برای کپی/جست‌وجو: همیشه از `base`ها ساخته شود نه DOM (به‌خاطر `user-select:none` روی rt).

## ۷. محدودیت‌ها / بدهی‌ها

- فقط **Chromium 156** تست شد (agent-browser فقط Chromium دارد). رفتار Firefox (Gecko روبی کامل‌تر دارد) و Safari/WebKit — به‌ویژه ترتیب bidi و رشد سطر — در FT-002 سه‌مرورگری باید تکرار شود؛ اعداد §۴ ممکن است در Gecko بهتر باشد (Gecko خط را برای روبی کامل باز می‌کند).
- سناریوی «انتخاب با درگ واقعی ماوس» فقط با API شبیه‌سازی شد؛ رفتار انتخاب لمسی موبایل دستی‌تست نشد.
- ارقام این گزارش با فونت‌های subset واقعی محصول گرفته شده (نه فونت سیستم) — اما با DPI/1x و headless؛ رندر HiDPI ممکن است جایگزینی گلیف بدهد.
