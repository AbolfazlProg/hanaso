# TASK-HANASO-20 — HTTP 409 FIX (ثبت با توضیح و مسیر بازیابی)

> Fixes audit BUG-004 (Medium) + the access-layer half of BUG-002. Verified by E2E S3 (4 browser checks) + `learner-isolation.spec.ts` (409 payload + recovery-path tests).

## مشکل

- ورود مستقیم به هر ایستگاه باز بود؛ ثبت تکمیل مشروط به پیش‌نیازها → ۴۰۹ بی‌توضیح؛ دکمهٔ «تلاش دوباره برای ثبت» همیشه شکست می‌خورد و علت را نمی‌گفت (کل تلاش درس به‌ظاهر هدر می‌رفت).

## رفع — بدون حذف Validation

`409` با «پذیرش Completion نامعتبر» رفع **نشده**؛ گیت prerequisite سرور دقیقاً همان است. سه چیز اضافه شد:

1. **Payload ساختاریافته** (`app/api/curriculum/station/route.ts`):
   - `error.message` فارسی: «برای ثبت این درس، ابتدا باید این درس‌ها کامل شوند: «عنوان۱» و «عنوان۲»»
   - `error.details.prerequisites = [{slug, titleFa}]` — **به‌ترتیب walk** (مرتب‌شده با `order` ایستگاه).
2. **پنل ساختاریافته در runner** (`station-runner.tsx`):
   - `[data-completion-failed="prerequisites"]`: عنوان «این درس هنوز قابل ثبت نیست» + علت + فهرست پیش‌نیازها + دکمهٔ **«رفتن به درس پیش‌نیاز: «عنوان»»** (لینک به اولین پیش‌نیاز برنشده — ورود عادی، نه `?mode=review`).
   - دکمهٔ retry بی‌هدف فقط برای این kind حذف شد (retry نمی‌تواند پیش‌نیاز را بپیماید)؛ retry عمومی برای خطاهای شبکه/5xx باقی ماند.
3. **مسیر بازیابی واقعی اثبات شد:** «رشد از h0 → h1 → سپس h2» در تست API: 409 → پیمایش پیش‌نیاز → 200 (E2E/API هر دو).

## Idempotency / دو درخواست هم‌زمان

- ثبت تکراری همان ایستگاه: `already: true` (بدون ردیف دوم) — از قبل موجود، حفظ شد.
- Precondition همان بررسی سرور-مرجع باقی ماند (هرگز سمت کلاینت اعتماد نمی‌شود).

## پذیرش PHASE 2 — نتیجه

- «کاربر جدید از اولین درس شروع کند، کامل کند و بدون 409 غیرموجه برگردد» ✓ (E2E S1.3 — کل مسیر بدون هیچ 4xx/5xx؛ 409 فقط برای حالت عمدیِ تست S3).
- ترتیب یادگیری حفظ شد ✓ (هیچ Completion نامعتبر پذیرفته نشد؛ گیت سرور دست‌نخورده).
