# TASK-HANASO-20 — ROOT CAUSE ANALYSIS (تحلیل ریشه‌ای)

## ۱) BUG-001 — بازدید اول، پیشرفت کاربر مشترک (Critical)

### زنجیرهٔ کامل داده (دنبال‌شدنی در کد)

```
Browser (بدون کوکی) → GET / → Next middleware (وجود نداشت!) → RSC render
  → resolveLearnerId() [lib/learner/server.ts:38]
  → کوکی hanaso_lid غایب → fallback: POC_DEFAULT_USER_ID ('poc-user')
  → resolveHome('poc-user') → استورهای پیشرفت → ردیف‌های واقعی poc-user
  → SSR HTML: «۴ ایستگاه کامل کرده‌ای» + «قدم بعدی: ردیف か»
```

### ریشه‌ها (سه لایهٔ مستقل که با هم زنجیره را ساختند)

1. **Server identity fallback (علت اصلی):** `resolveLearnerId()` و `resolveLearnerIdFromRequest()` بدون کوکی به شناسهٔ اشتراکی `poc-user` برمی‌گشتند (طراحی عمدی دورهٔ no-auth از TASK-LEARNING-08 با کامنت «falls back … only when the cookie is absent» — یعنی هر بازدید اولی = همان حساب مشترک).
2. **هیچ مکانیزم سمت سرور برای ساخت شناسه نبود:** ساخت id فقط در `LearnerIdBootstrap` (useEffect بعد از hydration) انجام می‌شد؛ RSC همان HTML اولیه را نگه می‌داشت و هیچ `router.refresh`/revalidate بعد از ساخت id انجام نمی‌شد — به همین دلیل محتوا حتی ۳+ ثانیه بعد از hydration هم اصلاح نمی‌شد (بازتولید زندهٔ ممیزی).
3. **CTA از پیشرفت آلوده تغذیه می‌شد (BUG-002):** برای `poc-user` ایستگاه‌های h0/h1 قبلاً کامل بودند؛ resolver حالتِ «resume» را برای کاربر تازه انتخاب کرد و CTA او را به h2 برد (درسی که پیش‌نیازهایش برای شناسهٔ تازه هرگز ثبت نشده بود).

### چرا ۴۰۹ رخ می‌داد (BUG-004)

```
POST /api/curriculum/station {action:'complete', station:'stn-kana-h2'}
  → resolveLearnerIdFromRequest: کلاینت بعد از hydration کوکی تازه ساخته بود → userId = id تازه
  → store.listForUnit(id تازه, prereqs) → هیچ ردیفی نیست
  → 409 station/prerequisites_not_met («station prerequisites not walked: stn-kana-h1»)
  → UI: دکمهٔ بی‌متن «تلاش دوباره برای ثبت» — بدون علت، بدون مسیر بازیابی
```

### آیا واقعاً نشت دادهٔ بین کاربران وجود داشت؟

**به معنای فنی: بله — از نوع «render-time contamination»، نه از نوع «cross-account read در یک session»:** هر بازدید بدون کوکی، دادهٔ REAL کاربر دیگری (`poc-user`) را SSR می‌کرد و آن را به عنوان پیشرفتِ خودِ بازدیدکننده ارائه می‌داد (متن + CTA). «حساب QA» بین کاربران به اشتراک گذاشته می‌شد؛ نوشتن در آن (مرورگرهای بدون JS که bootstrap ندارند) به «آلودگی دوطرفه» می‌انجامید. با this-fix: هیچ درخواستی بدون کوکی، دادهٔ هیچ کاربر دیگری نمی‌بیند و هیچ نوشته‌ای در حساب دیگر ثبت نمی‌کند.

## ۲) BUG-003 — تناقض きょう (High)

- **ریشه:** بلوک‌های تدریس TL-14 با قرارداد R1-03 (واکهٔ بلند = و اضافه: じゅう=جوو، きゅう=کیوو) هم‌راستا نشده بودند — سه بلوک + جدول کارت + `promptJaReading` می‌گفتند «کیو»، تنها گزینهٔ پذیرفته «کیوو».
- **کورِ گیت:** `TRANSCRIPT-CONSISTENT` فقط `reading`های ساختاری را با هم مقایسه می‌کرد؛ **برچسب گزینهٔ درست** را نمی‌دید — پاسخِ مطابقِ درس، غلط می‌شد.
- همان کلاس در ۵ واژهٔ دیگر هم پیدا شد (پس از تعمیم گیت): おおさか، えき، がくせい، がっこう (+ lis-1 きょう).

## ۳) BUG-005/006 — ترکیب خارجی و مشتقات کاتاکانا (Medium)

## ۴) BUG-007 — بازخورد کلی‌گو (Medium)
