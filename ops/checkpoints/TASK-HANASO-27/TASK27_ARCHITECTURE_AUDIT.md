## Section 5: Security & idempotency

- **userId**: signed `hanaso_lid` cookie (HMAC, httpOnly, Secure, SameSite=Lax, 1yr) minted GET-only by `src/middleware.ts`; `resolveLearnerId()` (RSC) / `resolveLearnerIdFromRequest(req)` (routes) in `lib/learner/server.ts` lines 63–93; invalid/unsigned → `GUEST_LEARNER_ID='guest'` (line 44), never the legacy shared `poc-user`.
- **Authz**: every state-changing action in `/api/curriculum/station` (route lines 179–187) and `/api/practice` (lines 93–98 GET, 163–171 POST) rejects guest with 401 `learner/no_identity`. Practice sessions are ownership-checked (`session.userId !== userId` → 404, lines 241–245, 286–291). Body-supplied userIds are never trusted. CSRF closed by Lax + JSON content-type.
- **Idempotency**: station `complete` → `already:true` when already completed (route lines 456–458); practice `recordCompleted` → `onConflictDoNothing` → `'already'`, fold skipped (`db/repositories/practice.ts` lines 74–90); both folds run in one transaction with `pg_advisory_xact_lock` per user (completions.ts lines 37–39, 80). Client adds single-flight guards (station-runner.tsx line 699).
- **Server-side content validation**: prerequisites enforced (409), criterion re-checked, hint restricted to the station's own practice exercises, writing character must be in station content (422).

## Section 6: Recommended integration design (minimal change)

1. **Reuse, don't rebuild**: author practice as **Stations** — `type: 'practice'` already exists in `STATION_TYPES` and in shipped content as the proven pattern. Practice stations should use the existing `exercise` block + the 4 kana exercise types (kana-recognition/recall/decode/listening) and `writing-practice` where needed — all already rendered by StationRunner and graded by `/api/curriculum/station`.
2. **Keep the generator as a content-authoring/server concern**: `generateKanaSession` can remain, but its output should map into curriculum `Exercise`/block records, so grading goes through the ONE `grade` action and the F-ladder/hint contract — retiring the parallel `answer` action and its 2-attempt ladder.
3. **Keep both evidence tables**: `practice_sessions` + `learning_object_states` are append-only evidence and the FSRS seam, not a parallel progress store — completion of a practice session should flow through the station `complete` action so the journey map reflects it, but the evidence fold must survive unchanged.
4. **Standalone `/practice`**: keep the page as a hub/entry point but deep-link sessions into `/learn/[chapter]/journey/[station]` stations rather than the inline `PracticeSessionRunner`; add journey-map linkage.
5. **Retire/quarantine**: `/poc/practice` + `modules/practice/{generator,checker,types}.ts` (root POC files) + `api/progress`/`progress-machine.ts` remain dev/test-only (already 404 in prod) — do not wire them in.
6. **Do NOT build**: a second scheduler, any FSRS queue now (port stays throwing), new block kinds (existing 17 suffice), client-side answer keys, or a new progress table. The `hint` action, audio maps, walk persistence, resume policy, and idempotent completion are all directly reusable as-is.

**Verdict:** the architecture is already ~80% aligned — the only true duplicates are the practice item/grading/ladder contract and its `generate/answer/complete` session API; everything else (stores, audio, completion service patterns, security) is shared or complementary.
