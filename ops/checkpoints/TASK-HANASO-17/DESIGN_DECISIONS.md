## ۱) یافته‌های کلیدی استخراج‌شده

1. **داشبورد = تصمیم، نه ویترین** [R dashboard §۱]: تک‌مأموریت «امروز چه کار کنم؟» و فرستادن کاربر به جلسه. ≤۶ بلوک اطلاعاتی، ≤۱۲ عنصر قابل‌کلیک.
2. **الگوریتم اولویت واحد** [R dashboard §۳]: قدم بعدی همیشه CTA اول؛ مرور دوم (هرگز جایگزین قدم بعدی نمی‌شود)؛ ≤۳ پیشنهاد جانبی با دلیل.
3. **PG-01 معتبر** [R page-design-specs §۲ DD-053]: اجزا: سلام کوتاه → کارت قدم بعدی → کارت مرور (شمار + پیش‌بینی) → ≤۲ پیشنهاد با دلیل → نوار هفته؛ RSC بدون اسپینر.
4. **ناوبری از قصد** [R nav v3 §۱-۲]: ≤۵ مقصد؛ جلسات غوطه‌ور بدون ناوبری اصلی؛ «کنترل مرده نساز» (جست‌وجوی ۱.۵)؛ بدون عنصر اضطراب‌ساز (عدد بدهی قرمز ممنوع).
5. **بازگشت پس از غیبت** [R behavioral §۴]: پیام خنثی، جلسهٔ اول کوتاه، بدون عدد منفی؛ ≥۷ روز = پنل بازگشت (در معماری ما: CTA «شروع دوبارهٔ درس»).
6. **FSRS not-integrated** [R integration.ts]: port صادقانه throw می‌کند؛ هیچ صف مروری وجود ندارد → هر عدد «مرور امروز» ساختگی است. آنتی‌پترن ممنوع: «دو سیستم مرور موازی».
7. **معماری موجود**: فصل فعال از Progress (reveal.ts)؛ Section = units[] مشتق‌شده؛ Resume = localStorage snapshot + server anchor (`currentBlock`)؛ `complete` از پیش Idempotent (`already:true`)؛ Pg جدول `station_progress` ستون‌های زمانی دارد اما DTO `StationState` آن‌ها را عبور نمی‌دهد.

## ۳) محدودیت‌های معماری فعلی

- بدون auth → بدون نام کاربر؛ learner id کوکی‌محور.
- بدون موتور مرور (M2) → کارت مرور نمی‌تواند عدد حقیقی نشان دهد.
- StationState فاقد timestamp در DTO → برای انقضا باید عبور داده شود.
- `enter` در هر mount اجرا می‌شود → اگر upsert همیشه `updated_at` را بزند، Refresh تمدید می‌کند (نقض §8.1) → تفکیک bump لازم است.
- localStorage snapshot خودش `updatedAt` دارد → همان سیاست freshness روی آن اعمال می‌شود (بدون وابستگی صرف به LocalStorage §10).
