# DEPLOYMENT_FAILURE_ANALYSIS — TASK-HANASO-16

> ۲۰۲۶-۱۱-۱۱ · تحلیل شکست انتشار `1.0.0-tl14-r01` و Rollback نادرست · مبنای شواهد: آزمون‌های زندهٔ شبکه در همین سشن

## ۱) گزارش شکست (ورودی مالک)

- اجرای یک‌خطی v8 (هدف: `1.0.0-tl14-r01` @ `935010f8`): preflight، backup، build، migrate، seed و **گیت سلامت داخلی C5 (ok:true + commit + version)** همه موفق.
- گیت **C7 عمومی** (`https://learn.kotodama.ir/api/health` از خود VPS): `curl: (52) Empty reply from server` → تلهٔ ERR → رول‌بک App به `1.0.0-tl13-r01`.
- در همان محیط، `kotodama.ir` (سرویس مستقل، دست‌نخورده) نیز Empty reply بود.
- نتیجهٔ مالک: «Production = 1.0.0-tl13-r01» (رول‌بک App موفق؛ سلامت محلی برقرار).

## ۳) تشخیص نهایی

1. **Endpoint عمومی هر دو دامنه برای کل دنیا خراب است** — نه مشکل Hairpin/Self-Probe محض، نه مشکل Application. الگوی دقیق: پذیرش TCP + خاتمهٔ TLS با گواهی معتبر (یعنی Reverse Proxy روی VPS زنده است و کلید خصوصی/گواهی دارد) و سپس **بستن اتصال بدون پاسخ HTTP** — امضای کلاسیکِ «Proxy زنده ولی upstream/backend آن پاسخ نمی‌دهد یا router مطابقت ندارد».
2. **این خرابی از قبل موجود بود** — شاهد: kotodama.ir (که Updater هرگز لمس نمی‌کند) دقیقاً همان‌طور خراب است؛ رول‌بک App (که فقط Image کانتینر web/worker را عوض می‌کند) طبیعتاً نمی‌توانست آن را درست کند و نکرد — الان هم خراب است.
3. **رول‌بک TL-14 نتیجهٔ درست ولی تشخیص نادرستی داشت**: App سالم بود (سلامت داخلی + نسخه درست)، ولی Updater توان تفکیک «خرابی Pre-existing خط مقدم» از «خرابی ناشی از انتشار» را نداشت، چون:
   - **Preflight فقط سلامت محلی را به‌عنوان Baseline می‌سنجد، نه مسیر عمومی را** → هنگام شکست C7 معلوم نبود مسیر عمومی از قبل خراب بوده یا تازه خراب شده.
   - گیت C7 هر شکست عمومی را «شکست انتشار» تفسیر و رول‌بک می‌کند — دقیقاً سناریوی مأموریت §۸.۲.
   - شاهد KOTODAMA (C10) فقط مقایسهٔ قبل/بعد است و در جریان شکست C7 اصلاً به آن نرسید/به تصمیم رول‌بک راه ندارد.
4. ریشهٔ احتمالی خرابی خط مقدم (نیازمند بررسی مالک روی VPS — خارج از دسترس این سندباکس؛ SSH موجود نیست): سرویس HAProxy/nginx میزبان (کانتینر یا سرویس systemd) که upstreamهایش را نمی‌بیند (مثلاً شبکهٔ Docker پس از فشار منابع/ری‌استارت دِی‌مِن، یا کانفیگ ACL/SNI ناقص شده، یا فایروال). **App و دیتابیس هاناسو جدا از این لایه سالم‌اند** (سلامت داخلی بعد از رول‌بک برقرار بود).

## ۴) سیاست اصلاح (پیاده‌سازی در DEPLOYMENT_GATE_FIX.md)

سه سطح سلامت + تفکیک پیش‌وجود بودن:

- **Tier 1 — Application**: `127.0.0.1:3100/api/health` (+ready) — شکست = مشکل App → رول‌بک.
- **Tier 2 — Local Ingress**: (2a) پروب مستقیم Proxy از روی خود Host با SNI/Host صحیح (`--resolve …:443:127.0.0.1`) و (2b) پروب URL عمومی از خود VPS (مسیر Hairpin کامل).
- **Tier 3 — Independent Public**: راستی‌آزمایی Endpoint عمومی از مسیری مستقل از VPS (check-host.net API — best-effort، بدون وابستگی سخت).

ماتریس تصمیم:

| Tier1 | Tier2a | Tier2b/T3 | تشخیص | اقدام |
| --- | --- | --- | --- | --- |
| ✗ | — | — | APP_FAILED | رول‌بک (همان امروز) |
| ✓ | ✓ | ✓ | DEPLOYED | موفق |
| ✓ | ✓ | ✗/نامعلوم | EXTERNAL_UNVERIFIED | انتشار می‌ماند؛ گزارش صریح؛ بدون رول‌بک |
| ✓ | ✗ از **قبل از انتشار** (Baseline) | ✗ تأیید بیرونی | **INGRESS_PREEXISTING_BROKEN** | توقف **قبل از هر تغییر** + دستور تشخیصی؛ بدون رول‌بکِ بی‌فایده |
| ✓ | ✓ در Baseline، ✗ بعد از انتشار | — | DEPLOY_BROKE_INGRESS | رول‌بک (انتشار واقعاً مسیر را شکسته) |

قواعد مکمل: Baseline عمومی جدید در Preflight ثبت می‌شود (کد + امضای خطا + شاهد kotodama + Tier3)؛ هیچ Health Check با `|| true` دور زده نمی‌شود؛ همهٔ خطاها verbatim چاپ می‌شوند؛ رول‌بک App هرگز دیتابیس/Volumes را لمس نمی‌کند (موجود — حفظ می‌شود).

## ۵) وضعیت انتشار فعلی (واقعیت، نه فرض)

- App روی VPS: به گفتهٔ مالک `1.0.0-tl13-r01` (رول‌بک موفق با سلامت محلی). **از بیرون قابل راستی‌آزمایی نیست چون مسیر عمومی قطع است.**
- مسیر عمومی: **خراب برای همهٔ دنیا** (شواهد §۲) — تا تعمیر خط مقدم توسط مالک، هر انتشار جدیدی به‌درستی باید متوقف شود (سیاست §۴) و باید ابتدا HAProxy/nginx میزبان تعمیر شود.
- KOTODAMA: از بیرون در دسترس نیست (همان خرابی خط مقدم)؛ شواهد داخلی وجود ندارد که خود سرویس آسیب دیده باشد — Updater هرگز آن را لمس نمی‌کند.
