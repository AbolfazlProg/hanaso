# sandbox-tests — آزمون‌های ایزولهٔ اسکریپت به‌روزرسانی یک‌دستوری (TASK-HANASO-DEPLOY-02)

این پوشه **هارنس آزمون** `infra/deploy/update-hanaso.sh` است: همان اسکریپت واقعی، بدون
Docker واقعی، بدون شبکه، بدون VPS و بدون هیچ لمسی به KOTODAMA.

## روش آزمون (صادقانه — این شبیه‌سازی است، نه Deploy واقعی)

- اسکریپت به‌روزرسانی **واقعی و بدون تغییر** اجرا می‌شود (`PATH` به `mock-bin/` اشاره می‌کند).
- `git` واقعی است: یک ریپوی ساختگی با دو کامیت (base = نسخهٔ زندهٔ شبیه‌سازی‌شده، target = انتشار)
  ساخته می‌شود و مکانیک `git worktree` واقعاً اجرا می‌شود؛ `origin` عامدانه غیرقابل‌دسترسی است.
- `docker` / `curl` / `df` **stub** هستند: هر فراخوانی در `calls.log` ثبت می‌شود؛ رفتار
  compose (up/run/exec/ps)، ساخت image و پاسخ‌های health/ready/kotodama از روی فایل وضعیت
  شبیه‌سازی می‌شود؛ نقاط شکست (build/migrate/backup/health/kotodama) با `config.env` تزریق می‌شوند.
- دایرکتوری deploy ساختگی، **فایل compose واقعی** `infra/deploy/learn-kotodama/docker-compose.shared-vps.yml`
  و `scripts/smoke.sh` واقعی را کنار یک `.env` ساختگی قرار می‌دهد.

## اجرا

```bash
bash infra/deploy/sandbox-tests/run.sh          # خروجی PASS/FAIL؛ exit 0 = همه سبز
bash infra/deploy/sandbox-tests/run.sh --keep   # نگه‌داشتن پوشهٔ کار برای بازرسی
```

## سناریوها

| #   | سناریو                                   | انتظار                                                             |
| --- | ---------------------------------------- | ------------------------------------------------------------------ |
| S1  | میزبان سالم، به‌روزرسانی به نسخهٔ هدف    | exit 0 · تعویض image · migrate · گیت سلامت · smoke · شاهد kotodama |
| S2  | از نسخهٔ قبلی + رفت‌وبرگشت rollback      | ثبت image قبلی · rollback زیرفرمان · به‌روزرسانی مجدد موفق         |
| S3  | نبود/خرابی Docker                        | شکست در preflight · صفر تغییر                                      |
| S4  | کمبود فضای دیسک                          | شکست در preflight با پیام روشن · صفر تغییر                         |
| S5  | قطع دسترسی GitHub                        | شکست fetch قبل از هر تغییری · راهنمای یک‌بارهٔ credential          |
| S6  | شکست Build                               | توقف **قبل از** تعویض .env · صفر تغییر                             |
| S7  | شکست Migration بعد از تعویض              | رول‌بک خودکار · بازگردانی image قبلی · گیت سلامت قبلی              |
| S8  | شکست گیت سلامت (نسخهٔ جدید بالا نمی‌آید) | رول‌بک خودکار                                                      |
| S9  | اجرای دوباره روی نسخهٔ هدف               | no-op کامل (بدون build/migrate/up)                                 |
| S10 | rollback از رکورد تاریخ                  | بازگشت image قبلی · health · smoke                                 |
| S11 | شکست بکاپ دیتابیس (اضافی)                | توقف قبل از هر تغییری                                              |
| S12 | خرابی شاهد kotodama بعد از تعویض (اضافی) | رول‌بک خودکار + گزارش INVESTIGATE                                  |
| S13 | زیرفرمان status (اضافی)                  | فقط-خواندنی، صفر جهش                                               |

در پایان، یک جاروی سراسری روی **تمام** سناریوها بررسی می‌کند که هرگز `compose down` اجرا نشده،
هیچ کانتینر غیر-hanaso لمس نشده و هیچ فرمان سراسری docker (prune/restart/stop/rm) صادر نشده است.

## محدودیت‌های صادقانه

- **Docker واقعی وجود ندارد** در سندباکس Agent؛ این هارنس **جریان کنترل، ترتیب مراحل،
  ترتیب فراخوانی‌ها، رفتار رول‌بک و حفاظت KOTODAMA** را آزمون می‌کند — نه خود Docker build،
  نه اتصال واقعی PostgreSQL، نه TLS/nginx واقعی.
- مسیر شبکهٔ sandbox به پورت ۲۲ VPS فیلتر است (سه تلاش کنترل‌شده، همگی TCP timeout)؛
  بنابراین Deploy واقعی توسط مالک با همان یک دستور نهایی انجام می‌شود.
- آخرین نتیجهٔ اجرا در `ops/checkpoints/TASK-LEARNING-08/CHECKPOINT_LOG.md` (CP مربوط به
  TASK-HANASO-DEPLOY-02) ثبت شده است.
